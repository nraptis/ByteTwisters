LightningMatrix Diversity Plan
==============================

Goal
----
Build a next-wave twister family that is much more diverse than the current byte-op search, can plausibly reach B/C grades on the new baseline-heavy report, and stays cheap enough to search in bulk.

Core Idea
---------
Use a small 4x4 byte matrix primitive, `LightningMatrix`, as the "expensive but still affordable" mixer. Each matrix is 16 bytes, and the new `PASSWORD_EXPANDED_SIZE = 7680` is cleanly divisible by 32, 48, and 192. That lets us use:
- 2 matrices as the default 32-byte walk
- 3 matrices as the heavier 48-byte walk

Recommended phase layout:

1. Load two or three 16-byte walks:
   - matrix_a from the current source walk
   - matrix_b from a shifted source or worker walk
   - matrix_c only in the heavier family
2. Run two cheap-op chains in phase 1:
   - chain_w writes directly into worker
   - chain_m writes entropy into matrix_a / matrix_b control state
3. Run 1-2 matrix-heavy transforms:
   - mostly on matrix_a
   - optionally cross-mix matrix_b into matrix_c
4. Finalize by mixing source bytes, worker bytes, and one or more matrix stores into dest

What LightningMatrix should be used for
---------------------------------------
LightningMatrix is not the whole twister. It is the "controlled chaos" component.

Good uses:
- take a weak local pattern and rearrange it without blowing the op budget
- create more structural diversity between candidates
- introduce cross-row and cross-column diffusion that the current byte ops do not have
- provide a source of parameterized expensive ops without forcing full cryptographic cost

Bad uses:
- replacing the entire twister with matrix ops
- using many slow whole-matrix transforms every loop
- treating matrix state as permanent global state

Recommended op families
-----------------------
Cheap ops: use 4-6 total per candidate phase group
- rotate row left/right
- rotate column up/down
- swap rows
- swap columns
- xor one row into another
- add one row into another
- xor one column into another
- add one column into another
- weave rows
- weave columns

Why these are good:
- tiny fixed loops
- parameter-rich
- mostly reversible or near-reversible
- diverse behavior without instantly collapsing low-entropy inputs

Expensive ops: use 1-2 per candidate, not per sub-step
- rotate right / rotate left (90 degree turns)
- transpose
- anti-diagonal flip
- ring rotation
- cross twist (rotate the center cross and fold in matrix totals)

Why these are good:
- they change the "shape" of the matrix, not just nearby bytes
- they create more diversity than plain row/column shifts
- they are still much cheaper than crypto-style rounds

Recommended generation model
----------------------------
Do not let the worker buffer act only as output. Let it also act as the control tape.

Example structure:

1. Cheap control bytes:
   - first few worker bytes decide:
     - how many cheap ops
     - how many matrix ops
     - which source walks to use
     - whether final mix is xor-heavy, add-heavy, or mixed
2. Cheap op pass:
   - 4-6 cheap ops chosen from a compact op table
   - apply to worker lanes and/or matrix_a
3. Expensive op pass:
   - 1-2 matrix transforms
   - optional cross-matrix combine:
     - matrix_a xor matrix_b
     - matrix_c add matrix_a
4. Final mix:
   - store one matrix back into worker or temp
   - combine source, worker, and matrix bytes into dest

How to get lots of diversity
----------------------------
1. Split candidates into templates instead of one giant recipe space.
   - template_row_bias: mostly row ops
   - template_column_bias: mostly column ops
   - template_cross_mix: more row/column xor-add ops
   - template_shape_shift: more rotate/transpose/ring ops

2. Randomize walk topology, not just arithmetic.
   - use different 16-byte sources for matrix_a, matrix_b, matrix_c
   - vary whether walks come from source or worker
   - vary whether the final store comes from matrix_a, matrix_b, matrix_c, or a blend

3. Separate "control entropy" from "data entropy".
   - worker bytes choose the ops
   - source bytes are what gets transformed
   - this prevents every candidate from behaving like the same byte-op chain with different constants

4. Use op buckets with hard caps.
   - at most 2 row swaps
   - at most 2 column swaps
   - at most 2 destructive mix ops
   - at most 2 whole-matrix ops
   - no candidate should be dominated by one trick

How to get higher test scores
-----------------------------
The current reports punish us mostly on zeros, ones, and predictable categories. So the new twisters need to do three things early:

1. Break symmetry fast.
   - row/column rotations and swaps should happen before nonlinear-ish add/xor mixing

2. Avoid easy fixed points.
   - do not use the same source walk for every local value
   - avoid final forms like `dest = xor(source, source_shifted)` with too little extra mixing

3. Spread information across both axes.
   - pure row logic or pure column logic will usually fail predictable inputs
   - every candidate should have at least one cross-axis step

4. Keep some near-reversibility in cheap ops.
   - too many destructive operations tend to collapse to low-entropy junk
   - use add/xor/swap/rotate more than overwrite-style behavior

5. Make the final combine asymmetric.
   - good example:
     - dest = add(source_mix, matrix_mix)
     - then xor with a shifted worker slice
   - bad example:
     - dest = xor(matrix_a, matrix_b) only

How to keep them fast
---------------------
1. Keep matrix size at 4x4 bytes.
   - 16 bytes fits natural walk sizes
   - easy to copy, rotate, and store

2. Prefer row ops over full remaps.
   - row ops are cheaper and branch-light
   - use whole-matrix transforms only as accents

3. Limit expensive ops to 1-2 per candidate loop.
   - that is enough to create diversity without blowing throughput

4. Reuse loaded data.
   - once matrix_a / matrix_b / matrix_c are loaded, squeeze multiple cheap ops out of them before reloading

5. Keep op dispatch compact.
   - small enum tables
   - modulo-small-range parameter decode from worker bytes

Recommended candidate budget
----------------------------
Target per candidate:
- 4-6 cheap ops
- 1-2 matrix-heavy ops
- 2-3 final combine ops

That should keep candidates visibly heavier than the current twisters, but still nowhere near world-class counter cost.

Suggested first search wave
---------------------------
Wave 1 should stay conservative:

- 2-matrix candidates as the default family
- 3-matrix candidates as the heavier family
- 8-10 cheap op choices
- 4-5 expensive op choices
- final op limited to `ADD` or `XOR`
- no nested matrix loops
- no more than 3 matrices live at once

Success criteria for Wave 1
---------------------------
We are trying to:
- beat the current generated twisters decisively
- survive zeros/ones/predictable categories more often
- produce regular B/C candidates in the report
- stay fast enough that search is still practical

Practical next implementation step
----------------------------------
Integrate `LightningMatrix` into the generator as a matrix-first candidate family, keep 2-matrix walks as the default search shape, and use 3-matrix walks as a higher-diversity variant.
